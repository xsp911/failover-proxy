# Failover Proxy

Отдельный OpenAI-совместимый прокси резервирования. Без зависимости от LiteLLM.

## Интерфейс и локальный запуск

Панель v0.22 — готовые HTML/CSS/Vanilla JavaScript, локальные SVG-иконки и системные шрифты. Нет React, Vite, Webpack, frontend-сборки, обязательного npm/Node.js или CDN для запуска панели. FastAPI раздаёт статические файлы напрямую. Отдельный существующий числовой детектор при включении использует Node; при его отсутствии панель и основной gateway запускаются, детектор недоступен.

Linux: `python3 -m venv .venv`, затем `.venv/bin/python -m pip install -r requirements.lock` и `.venv/bin/python tools/run-local.py`.

Windows: `py -3.12 -m venv .venv`, затем `.\\.venv\\Scripts\\python.exe -m pip install -r requirements.lock` и `.\\.venv\\Scripts\\python.exe tools\\run-local.py`.

Первый запуск запросит новый логин/пароль; данные по умолчанию в пользовательском профиле, не в production. Подробности, безопасность и ограничения проверки Windows: [инструкция](<../docs/RUNNING.md>). Дизайн-система и аудит: [DESIGN](<../docs/DESIGN.md>), [FRONTEND-AUDIT](<../docs/FRONTEND-AUDIT.md>). Проверка готовых локальных ресурсов без сборки: `python tools/check-web.py`.

## Что реализовано

- `/v1/models`, `/v1/chat/completions` (JSON и SSE); Responses/Anthropic API пока не поддерживаются.
- Несколько алиасов моделей, маршруты и приоритеты поставщиков.
- По одной попытке на доступного поставщика, общий лимит попыток и времени.
- Cooldown в памяти процесса; после истечения основной снова приоритетен. Перезапуск сбрасывает cooldown, не статистику/конфиг.
- Полная буферизация каждой генерации: ни текст, ни reasoning, ни tool arguments не выдаются до проверки upstream.
- EOF без настоящего `finish_reason`, некорректные SSE/JSON/tool arguments, сетевые ошибки, timeout, HTTP429/5xx и известный текстовый баннер запускают резервирование. HTTP401/403 одного поставщика также допускают резерв; клиентские HTTP400/413/422 не повторяются.
- Настоящие `length` и `content_filter` сохраняются как решения upstream, не выдаются за транспортный сбой.
- Отсутствие `[DONE]` при настоящем `finish_reason` допускается для совместимости. Чистый EOF без терминального reason — ошибка.
- Нативная передача `thinking`, `reasoning_effort`, изображений, tools и прочих JSON-полей без преобразований SDK.
- Клиент получает завершённые SSE-чанки успешного поставщика либо финальную JSON-ошибку до начала ответа. Нет живого появления токенов.
- Уже исполненные клиентом инструменты прокси не запускает и не повторяет. Повторяется только текущий модельный запрос; каждый поставщик может начислить оплату.
- Ограничения размера тела/ответа, количества SSE-чанков, параллельности и времени. Слот удерживается до передачи ответа клиенту, медленный клиент ограничен 30 сек на передачу. Отмена отключает upstream.

## Диагностика, очередь и совместимость

- При заполнении рабочих слотов запрос ждёт в FIFO-очереди до 3 секунд. Очередь не более 32 запросов; тела ожидающих запросов не буферизуются приложением. При истечении ожидания/переполнении — `429 gateway_capacity`, `Retry-After: 1`, `X-Request-ID`. Занятый медленной передачей ответа слот остаётся занятым до освобождения/таймаута. Очередь не добавляет попыток к поставщикам.
- Ошибки upstream читаются ограниченно (до 8 KiB), клиенту возвращаются только контролируемые диагностические объяснения. Сырые сообщения поставщика не копируются, чтобы не раскрыть ключи, URL, промпты и ответы.
- Подтверждённая структурированным кодом или точной формулировкой ошибка контекстного окна становится `400 context_length_exceeded`, без оставшихся попыток и без cooldown исправного поставщика. Неизвестные ошибки остаются классифицированы по HTTP/протоколу. Если первые поставщики ответили 502 без сведений о контексте, заранее определить превышение всё ещё невозможно.
- Успешные JSON/SSE-ответы содержат `X-Upstream` — безопасное ASCII-имя обслужившего поставщика (для не-ASCII имён — ID). Это не гарантирует сохранение промпт-кеша; sticky-маршрутизация не добавлена.
- `response_format` передаётся без изменений как **best effort**. Если upstream его игнорирует, прокси не обещает JSON/JSON Schema валидность. Клиент обязан проверять формат/схему и учитывать `length`/`content_filter`.
- Исходный `usage`, включая `total_tokens`, сохраняется в JSON/SSE без нормализации. Сумма известных IN+OUT в панели вычисляется отдельно; она может отличаться от заявленного upstream total и не является доказательством списания денег. Плату за неудачные попытки определяет поставщик, не нулевая метрика шлюза.
- В non-stream `reasoning_content` не синтезируется: отсутствие означает, что поле не передал upstream, а не отсутствие внутренних рассуждений.
- На HTTP кнопка копирования использует Clipboard API, затем проверяемый резервный механизм; при отказе остаётся ручное выделение и Ctrl+C.

## Учётная запись администратора (v2)

В **Настройки → Учётная запись** можно изменить логин и/или пароль. Для каждого изменения требуется текущий пароль и CSRF действующей сессии. Новый пароль — от12 до1024символов; пустое поле сохраняет текущий пароль при смене логина. После успешного изменения все старые сессии завершаются, необходимо войти заново. Логин/пароль сохраняются вБД, restart не восстанавливает начальные FP_ADMIN_* изenv. Действующие APIключи агентов не изменяются. Начальный access.env после ручной смены пароля не является источником текущего пароля; храните новые данные вменеджере секретов.

Карточка APIключа показывает только префикс. Полный ключ выдаётся один раз при создании, вБД хранится SHA256 и восстановить его нельзя. Кнопка **«Забыть»** — не скрытие карточки: после подтверждения ключ окончательно удаляется, доступ всех его клиентов прекращается. Для временной паузы используйте **«Отключить»**.

## Веб-панель

Поставщики: URL, ключ (только запись, пустое поле сохраняет прежний), приоритет, включение/отключение, проверка `/models`.

Модели: внешний алиас, `supports_vision`, необязательные `context_length` и `max_output_tokens`, маршруты и реальные имена моделей поставщиков. Пустые лимиты означают неизвестное значение (`null` в `/v1/models`). Это метаданные для клиента, не приближённое отсечение запроса: оценка «символы / 4» не используется. Указывайте проверенный общий лимит алиаса, поддерживаемый нужными маршрутами; значение не подбирается автоматически по каталогу одного поставщика.

Ограничения: таймауты, лимиты размера, попыток, параллельности, cooldown. Приватные upstream запрещены по умолчанию; разрешайте только для своей доверенной сети.

Ключи: отдельные клиентские токены, ограничения по моделям, отзыв/отключение. Полный токен показывается один раз, в БД хранится SHA256.

Статистика: клиентские запросы отдельно от попыток, успехи/ошибки, резервирования, IN/OUT/cache, TTFT upstream, первый ответ клиенту, TPS, p50/p95, последние ошибки и запросы без содержимого. Новая история начинается с запуска этого сервиса; LiteLLM-история не смешивается.

## Встроенные проверки моделей (lm-detector)

Алгоритм и эталонные данные `Ikaleio/lm-detector` встроены локально по MIT, версия исходника `4dcb4216151cbd5066d515297720130a9fd3b198` (25 октября2026). Отдельный сервер/порт исходного проекта не запускается. Локальный Node-процесс выполняет только числовой скоринг, без сети и без API-ключей. Происхождение, лицензия и контрольные суммы — в `detector/NOTICE`, `detector/provenance.json`, `detector/README.md`.

**Не доказательство подлинности.** Это замкнутый рейтинг сходства среди 63 эталонных моделей. Даже неизвестная модель может получить высокий балл ближайшего кандидата. Порог (настраивается вручную от50 до100%, по умолчанию95%) — административная политика по оценке выбранного эталона, не вероятность того, что поставщик честен. Используйте дополнительную проверку и фиксированные параметры.

Вкладка **Проверки моделей**:
- Ручной выбор добавленного поставщика, произвольного API-имени модели и точного эталона из каталога. При отсутствии модели в базе нельзя достоверно назвать её — выбирается ближайший кандидат с предупреждением, автоматических алиасов нет.
- Обычная проверка делает3 платных запроса (числовые задания) напрямую выбранному поставщику, без резервирования. При временной ошибке повторяется только сбойное задание до2раз с задержками2с/5с; успешные ответы текущего раунда сохраняются в памяти. Если оценка ниже порога, автоматически выполняется второй полный раунд из3 заданий для подтверждения, до18 upstream-вызовов в худшем случае с повторами. Результат не смешивается с рабочей статистикой запросов. Разрешено проверять временно исключённые и вручную отключённые поставщики.
- Мониторинг по умолчанию выключен, период30мин, настраиваемый5..1440мин. Для включения все включённые маршруты должны иметь выбранный эталон. При добавлении нового маршрута сначала отключите мониторинг, сохраните маршрут, настройте для него эталон, затем включите мониторинг снова. Включение запускает цикл сразу; далее период отсчитывается от начала цикла. До3 тестов разных поставщиков выполняются параллельно, у одного поставщика — один тест за раз; три задания одного теста последовательны. Локальный скоринг выполняется по одному, чтобы не раздувать память Node. Очередь ограничена64; уже выполняющийся тест не дублируется.
- Полный калиброванный результат из3 валидных ответов: оценка нужного эталона >= выбранного порога — `Совпадает`; ниже порога — `Ниже порога`. Новая блокировка требует двух полных калиброванных раундов ниже текущего порога; один низкий результат запускает подтверждение, а ошибка/неопределённость подтверждения не создаёт карантин. Если хотя бы одна контролируемая модель подтверждённо ниже порога, весь поставщик исключается из рабочего пула; проверочные запросы продолжаются и могут вернуть его после результата >= выбранного порога. Изменение порога сразу пересчитывает допуск по последнему определённому результату, без новых API-запросов; история исходных проверок не переписывается, переход отмечается источником «Изменение порога».
- Ошибка API, недостаточные числа, неизвестный эталон, отсутствие калибровки, не-модельная последовательность — **неопределённый результат**, не доказательство подмены. Такая проверка не снимает прежнее исключение и не создаёт новое без заключения.
- Карантин хранится отдельно от ручного `enabled`. Отключение мониторинга сразу снимает только его влияние; вручную отключённый поставщик автоматически не включается. При изменении URL/ключа/версии детектора старый результат не переносится на новый backend.
- Изменения конфигурации во время долгой проверки делают её результат неактуальным; он не исключит нового поставщика.

Вкладка **Журнал проверок** содержит только первое определённое состояние и переходы `Совпадает ↔ Ниже порога`. Повторные одинаковые оценки и сетевые ошибки не порождают записи журнала. Последняя попытка видна отдельно на вкладке проверок. Состояние сохраняется после перезапуска; журнал и краткие результаты ограничены сроком/количеством, сырые ответы заданий, ключи и промпты не сохраняются.

Для каждого задания сохраняются ожидаемое/фактическое/минимальное количество чисел, принятый `finish_reason`, количество попыток и безопасные коды ошибок; текст числовых ответов/рассуждений не записывается. `3/3` относится к текущему раунду, подтверждение показывается отдельно. `length`/другое неуспешное завершение или недостаток чисел не используются для финальной оценки; временные сбои задания повторяются в пределах бюджета. Точные структурированные HTTP500/SSE-коды `upstream_timeout` отображаются как `upstream_timeout` (HTTP504), без раскрытия произвольного текста upstream.

Технические ограничения: не более1800сек на всю проверку, включая подтверждение и повторы,250сек на запрос,16MiB SSE-данных и65536 кадров на запрос,65536 символов полезного числового ответа,8192 выходных токена. Проверочный сборщик не хранит историю кадров и reasoning, но проверяет ошибки, finish_reason и обрыв; рабочий collector/лимиты клиентских запросов не меняются, локальный скоринг45сек/256MiB Node heap. Отмена останавливает текущий запрос/скоринг; после начала короткой атомарной записи завершённого результата отмена уже не принимается. Проверки могут оплачиваться и при неудаче; для3 поставщиков каждые30мин обычный успешный режим —432 запроса в сутки; подтверждения и повторы могут увеличить верхнюю оценку до2592 вызовов (без ручных проверок, общий временной бюджет ограничивает фактическое число). Один worker по-прежнему обязателен.

## Настройки A6API

Вкладка **A6API** хранит консольный PAT и числовой ID аккаунта для Marketplace. PAT шифруется существующим Fernet-ключом внутри конфигурационной записи; в браузер возвращается только маска вида `jZqE********==`, полный токен не показывается никогда. Пустое поле PAT при сохранении оставляет прежний секрет; смена одного ID разрешена. Кнопка «Проверить доступ» выполняет только чтение (`/api/user/self` и `/api/token/`), ничего не закрепляет и не снимает.

Relay-ключ `sk-…` для `/api/*` не подходит. PAT даёт доступ к аккаунту целиком, поэтому храните его только здесь и отзывайте при компрометации. Пин постоянный и привязан к паре токен+модель; параллельно проверять разных продавцов нельзя.

## Cookie сессий между экземплярами

Cookie не разделяются по порту: два экземпляра на одном IP с одинаковым именем cookie перезаписывают сессию друг друга. Имя задаётся переменной `FP_COOKIE_NAME`: экземпляр `8843` использует `fp_admin_session_8843`. Задавайте уникальное имя для любой новой копии; настройки других экземпляров здесь не меняются.

## Защита

- Администратор PBKDF2; HttpOnly/SameSite cookie, CSRF и origin-проверка, ограничение попыток входа.
- Ключи поставщиков и консольный PAT шифруются Fernet в SQLite `proxy.db`; ключ шифрования — `secret.key` в фактическом `FP_DATA_DIR` экземпляра (обычно `/opt/failover-proxy v2/data`). Права каталога0700, файлов0600. Без этого ключа конфигурационные секреты не восстановить.
- Никаких промптов, ответов, URL с секретами или сырых исключений в статистике.
- Upstream только HTTPS/public IP по умолчанию, DNS-проверка и привязка соединения к проверенному IP с TLS SNI исходного hostname. Redirect запрещён; keepalive отключён для исключения междоменного reuse IP-origin TLS.
- HTTP-прокси из переменных окружения не используются. Приватные upstream — осознанное административное ослабление SSRF-защиты.
- Один worker обязателен: admission/cooldown в памяти. Для нескольких процессов нужен общий координатор.
- systemd: непривилегированный пользователь, read-only filesystem, 1GiB memory cap, автозапуск.

## Управление

Используйте фактическое имя systemd unit именно экземпляра v2. Не перезапускайте одноимённый старый сервис по инструкции для другого экземпляра. Операционные инструменты ниже не меняют systemd, firewall, production-конфигурацию и не запускают сервер.

Провайдеры и настройки применяются без перезапуска. Сохранение с ревизией защищает от перезаписи изменений другой вкладки. Изменение конфигурации сбрасывает текущий cooldown для новых запросов.

### Онлайн-бэкап и проверка

[backup.py](<../tools/backup.py>) читает все верхнеуровневые `*.db` через SQLite online backup API, включая committed WAL, и копирует только существующий `secret.key`. Данные приложения не инициализируются и не изменяются инструментом. Выход — **новый** каталог0700, файлы0600, [формат manifest](<../tools/operational.py>) с SHA256, размерами, временемUTC и версиейSQLite. Каталоги должны быть абсолютными, непересекающимися, без symlink; существующий выход не перезаписывается. При сбое неполный каталог остаётся для ручной проверки, автоматического удаления нет. Каждый файлSQLite согласован отдельно: общей транзакции несколькихБД нет.

```bash
cd '/opt/failover-proxy v2/app'
PYTHON=/home/xspider/failover-proxy/.venv/bin/python
# Родительский каталог резервных копий должен уже существовать и быть защищён.
"$PYTHON" tools/backup.py --data-dir '/opt/failover-proxy v2/data' \
  --output-dir /absolute/private-backups/new-snapshot
"$PYTHON" tools/verify-backup.py --backup-dir /absolute/private-backups/new-snapshot
```

[verify-backup.py](<../tools/verify-backup.py>) проверяет права, перечень файлов, SHA256, `PRAGMA integrity_check` каждойБД и расшифровку всех непустых `*_encrypted` в конфигурации ключом из копии. Ключи и расшифрованные значения не печатаются. Проверка требует `cryptography` из lock-файла; обе команды не обращаются к сети. Если `secret.key` отсутствует, копируется толькоSQLite; зашифрованная конфигурация без ключа проверку не пройдёт. Manifest защищает от случайного повреждения, **не является подписью** против подмены вместе с файлами. Резервная копия содержит ключ, пароли/сессии/конфигурацию: храните её как секрет, отдельно шифруйте при передаче/долгом хранении.

Автоматического восстановления в production нет. Сначала копируйте проверенный снимок в **новый временный каталог**, проверяйте там загрузку и расшифровку; переключение рабочего экземпляра — отдельная ручная процедура с остановкой правильного сервиса. [Тесты инструментов](<../tests/test_operational_tools.py>) восстанавливают только временную тестовуюБД с синтетическими секретами. `access.env`, TLS и произвольные файлы не входят в allowlist: храните нужную конфигурацию развёртывания отдельно защищённым способом. Начальный `access.env` не является источником авторизации после созданияБД: изменение текста пароля там не меняет PBKDF2 запись.

## Разработка и проверки

Самостоятельный Python-проект: Python3.12+, зависимости зафиксированы в [requirements.lock](<../requirements.lock>). Версия берётся из [proxy/__init__.py](<../proxy/__init__.py>), а не из устаревшего номера в документации.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
FP_PYTHON="$PWD/.venv/bin/python" bash tools/check-release.sh
# Для существующей среды этого хоста:
FP_PYTHON=/home/xspider/failover-proxy/.venv/bin/python bash tools/check-release.sh
# Только перечень офлайн browser-контрактов:
FP_PYTHON=/home/xspider/failover-proxy/.venv/bin/python bash tools/check-release.sh --list-browser-contracts
# Pytest + офлайн browser-контракты:
FP_PYTHON="$PWD/.venv/bin/python" bash tools/check-release.sh --browser-contracts
```

[check-release.sh](<../tools/check-release.sh>) запускает офлайн secret-check, `pytest` выбранным virtualenv Python и [release-report.py](<../tools/release-report.py>) с фактическим результатомpytest. Сеть, установка зависимостей, git commit/push, сервер, credentials и настройки сервисов не используются. Некоторые pytest-проверки скоринга уже требуют Node. Browser-контракты требуют Node, Playwright, установленный Chromium и его системные библиотеки; существующие тесты ищут `require('playwright')` (можно через `NODE_PATH`), затем `/tmp/failover-browser-check/node_modules/playwright`; часть старых контрактов использует только второй путь. Зависимости браузера устанавливаются **отдельно**, не release-скриптом.

Только явно перечисленные офлайн mock-контракты включены в gate. [browser.cjs](<../tests/browser.cjs>), [browser-feedback-live.cjs](<../tests/browser-feedback-live.cjs>), [browser-detector-live.cjs](<../tests/browser-detector-live.cjs>) — старые live-сценарии, автоматически не запускаются: могут читать реальные credentials и обращаться к сервису. Офлайн pytest не использует реальные ключи и платных поставщиков; ASGI-проверки покрывают отмену, backpressure и освобождение буфера.

[check-secrets.py](<../tools/check-secrets.py>) — Python stdlib, без сети: проверяет tracked и неигнорируемые untracked исходники; исключает `.env`/`*.env`, данныеБД, ключевой файл, бинарные файлы, кэши и зависимости. Выводит только файл/строку/тип, не совпавшее значение. Узкие форматы известных токенов и private-key-заголовки избегают ложных срабатываний на длинные hash; это эвристика, не гарантия отсутствия секретов. Синтетическую строку можно явно отметить `secret-check: allow synthetic`; реальные секреты так не исключайте.

```bash
.venv/bin/python tools/check-secrets.py
.venv/bin/python tools/release-report.py --test-result not-run
```

Release-report выводит версию, gitSHA, dirty status и явно **переданный вызывающим** результат тестов; сам тесты не запускает. Ничего не публикует. Настройки и частоты проверок моделей, мониторинга и пулов операционными инструментами **не изменяются**.

Это самостоятельный проект, не форк LiteLLM. Компоненты числового fingerprint-скоринга взяты из lm-detector с сохранением лицензии и provenance. Для расширения добавляйте новые протоколы отдельными адаптерами и тестами, не универсальными эвристиками над текстом.
