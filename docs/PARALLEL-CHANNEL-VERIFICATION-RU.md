# Параллельная верификация каналов: мульти-токенные лейны (RU)

Как превратить последовательный опрос каналов в параллельный конвейер.
`CHANNEL-PROBING-NOTES.md` отвечает на вопрос «что проверять в каждом канале»
(отпечаток, промпт-токены, рисунок, движение, потолок); эта заметка — «как гонять
много каналов одновременно», чтобы пробы не мешали друг другу — и что это экономит.
Цифры ниже из реальных партий на одном реселлере; переносим метод, а не числа.

Английская версия: `PARALLEL-CHANNEL-VERIFICATION.md`.

## Инвариант, который делает параллельность бесплатной

На OpenAI-совместимых маркетплейсах маршрут ключа для модели — свойство **пары
(токен, модель)**. Две пробы конфликтуют, только если совпадают И токен, И модель.
Отсюда всё остальное:

- N параллельных лейнов на **одной модели** требуют N **разных токенов**;
- **один и тот же токен** может обслуживать два лейна на **разных моделях**
  одновременно — записи подписок никогда не касаются одного объекта;
- 10 лейнов на 2 моделях требуют всего 10 токенов: каждый ключ работает сразу в двух
  парах, `(ключ, модель-A)` и `(ключ, модель-B)`.

Если токен один — параллелить пробы одной модели без драки за подписку не выйдет.
Сначала заведи пачку технических ключей: этот пул и есть весь бюджет параллельности.

## Паттерн лейна

Один лейн = один токен = одна очередь каналов:

1. **Пин**: подписку лейна `(токен, модель)` выставить на проверяемый канал
   (обычно — высший доступный для записи приоритет маршрута).
2. **Проба**: полная батарея проверок через этот токен.
3. **Рестор**: вернуть подписку к базовому набору маршрутов — токен возвращается
   в нормальный трафик.
4. Следующий канал в очереди.

Опасный шаг — (3): рестор может упасть (маркетплейс может отдать 400
«channel disabled or unavailable», пока пин ещё стоит). Лейн никогда не должен
завершаться, оставив токен запиненным. Две защиты:

- **kill-safe heal**: если лейн умер посреди пробы, внешний супервизор должен уметь
  повторить рестор независимо от мёртвого лейна — восстановление из сохранённого
  снапшота базлайна, не из памяти умирающего процесса;
- **рестор фильтрует базлайн по живому каталогу маркетплейса** — исчезнувшие каналы
  выбрасываются. Жди, что восстановленный маршрут будет на пару каналов короче
  исходного; это не потеря.

## Стена — это максимум, а не сумма

Серия: 20 каналов × ~13 мин = 4.2 часа. Параллельно (10 токенов, 2 модели, волна
по 5 лейнов): стена волны равна **самому медленному каналу в ней**, не сумме.

| | серия (20 кан.) | параллельно (10 кан., 5+5 лейнов) |
|---|---|---|
| стена | 4.25 ч | 0.81 ч (25 + 23 мин на волну) |
| стена на канал | 12.75 мин | 4.9 мин |
| каналов на час стены | 4.7 | 12.3 |
| расход на канал | $0.0043 | $0.0029–0.0039 |

Два свойства, которые стоит усвоить:

- **Пропускная способность растёт от лейнов, а не от денег.** Пять подписок
  одновременно поднимают расход на час стены (~1.8×), но партия заканчивается в
  2.6 раза быстрее — и каждый канал всё равно дешевле серии, потому что медленные
  каналы перестают блокировать быстрые.
- **Волна медленней своего худшего члена.** Один 25-минутный канал определяет волну;
  четыре 6-минутных закончат и простоят. Группировка каналов по ожидаемой латентности
  (быстрые с быстрыми) выжимает больше волн из того же часа — но только если латентности
  уже известны; при первом контакте смешанные волны нормальны.

## Вердиктам нужна политика повторов, а не только пороги

Два класса вердиктов одинаково выглядят за один прогон — и не одинаковы:

- **Транспортный эпизод** — запрос «успешен» на шлюзе, стрим «завершился», но контент
  пуст (маркетплейс мигнул, стрим закоммитился без usage). Канал может быть совершенно
  честным. **Всегда перепробуй один раз, прежде чем поверить в `dead` /
  `insufficient_data`.** В реальной партии: 1 из 10 каналов выглядел мёртвым с первого
  захода; повтор отрисовал чисто, отпечаток вернулся на 99.7 %.
- **Настоящий дрейф** — вероятность отпечатка для заявленной модели рухнула, локальный
  классификатор называет *другую* модель, а счётчики токенов остаются в честном
  коридоре. Один прогон — довод, не вердикт: перепроверяй в следующей партии, и
  считай однозначной только тройку (чужой топ-предикт + названная чужая модель +
  вероятность ниже ~0.1 %).

И заложи бюджет на повтор: на некоторых маркетплейсах пустой ответ всё равно
биллится (`gateway_estimate` по доставленному стриму). Мелочь, но повтор стоит
больше нуля даже когда первая попытка не дала ничего.

## Ре-верификация — не опция

Чистая проба покупает доверие ровно до следующей пробы. В партии ре-верификации,
описанной выше, каналы, прошедшие полную батарею за несколько дней до этого,
вернулись с другой моделью — три из пяти на одном лейне, включая маршрут высшего
приоритета в живом пуле. Работающий ритм: ре-верифицировать каждый канал, кормящий
продуктовый трафик, одновременно с апробацией очередной партии новых. Предельная
цена — центы; альтернатива — продуктовый трафик молча уходит на модель, которую
никто не выбирал.

## Чек-лист оператора

- [ ] N токенов заведено, уникальность значений проверена (дубли молча схлопывают лейны)
- [ ] снапшот базлайна маршрутов сохранён по каждому токену до первого пина
- [ ] выход лейна всегда выполняет рестор; супервизор умеет лечить мёртвый лейн из снапшота
- [ ] рестор аккуратно выбрасывает исчезнувшие каналы (число маршрутов может уменьшиться — это норма)
- [ ] вердикты `dead` / `insufficient_data` перепроверены один раз перед записью
- [ ] расход сверяется по логу запросов самого маркетплейса, а не по прайс-листам
- [ ] для каждого продуктового канала запланирована ре-верификация
