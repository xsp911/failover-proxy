# Управляемые A6API-пулы (8843)

## Несколько моделей

В главном разделе **A6API → Управляемые пулы** можно создавать независимые политики для разных моделей: рабочий token_id+точное model, от1 до4 отдельных тестовых токенов, ожидаемый fingerprint-эталон, протокол Chat/Responses, до четырёх необязательных ценовых потолков USD/1M (пустое поле — без ограничения; можно задать только цену выхода), минимум cache hit24h, успешность, TTL, лимиты кандидатов/участников/платных запросов и USD-бюджет.

Рабочий токен может обслуживать несколько моделей, если test token каждой политики отдельный. Тестовый токен не может одновременно быть рабочим токеном любого пула. На один token+model — одна политика. После публикации идентичность рабочего/тестового токена и модели не редактируется без специального detach (пока не реализован).

Секреты PAT остаются в Настройки→A6API; pool API не возвращает relay-ключи. Исправлено сохранение PAT при обычном изменении поставщиков: шифротекст больше не попадает в routing config и не теряется при save.

## Правильный путь проверки

- Кандидаты берутся из token-specific `/api/marketplace/channels/search`, вся пагинация, exact model/token, настоящий `cache_hit_rate_24h` (bps/100). Cache hit строго больше выбранного минимума; неизвестное не0.
- Сначала локальные цена/кеш/успех/единицы фильтры, затем ограниченная проверка. Лимит кандидатов задаёт размер отображаемой подборки, а не тупик поиска: проверка перебирает полный подходящий каталог, пока не наберёт max_members, не исчерпает бюджет или каталог. Уже выполняющиеся до4проверок завершаются, поэтому возможно немного больше удачных результатов, чем целевой размер пула.
- Сначала проверяются новые channel_id, которых ещё нет в истории. Неуспешная законченная проверка ставит продавца на паузу24часа; до её окончания он не расходует бюджет в повторных наборах. Потом одна следующая проверка снова разрешена; четыре подряд seller-fail по-прежнему ведут вбан. Cancel/budget/configchange не являются отказом продавца и не должны откладывать его как неудачный тест. Часовой аудит действующих участников намеренно не подчиняется очереди нового отбора: он обязан проверять участников каждыйчас. После него состав может сразу пополняться из ранее проверенного резерва: только freshverified с валиднымTTL, текущими ценами/cache/успешностью и безбана, не из неудачных/неаудированных бывших участников текущегоаудита. Это одна итоговая публикация без дополнительной платнойгенерации или отдельногоrefresh черезминуту.
- Полный поиск тестового токена кешируется не более60сек на одного исполнителя. Серверные caps, singlechannel и точная атрибуция остаются обязательны при каждом запросе; кеш каталога не разрешает обход ценовых ограничений.
- На **отдельном тестовом токене** создаётся одно-канальный manual-only маршрут с caps. Никаких пинов, auto_pool=false, fallback=false.
- Существующая чужая подписка тестового токена не перезаписывается. Управляемый тестовый маршрут имеет durable ownership/version; неопределённая запись блокирует продолжение до reconciliation.
- Обычный relay-ключ, не суффикс. После каждого synthetic запроса обязательна корреляция request_id→token_id→actual_channel_id; mismatch/fallback/нет лога дают unknown, никогда verified.
- Три fingerprint задания, низкая оценка требует второго полного раунда. Chat и Responses SSE валидируются разными обработчиками. Модель вне эталонной базы не признаётся точной: для gpt6.1 пользователь выбирает общий `gpt-6-astra/6.1-sol` с явной оговоркой.
- Проверка не исполняет tool calls и не записывает тексты запросов/ответов. Перед запросом создаётся pending-резерв worstcase; после запроса exactrequest_id+token_id связывается с журналомA6API и денежный учёт заменяет резерв на **quota/quota_per_unit**. quota_per_unit читается из/api/status (на проверенной платформе500000USDunit), не предполагается по ценам модели. ОшибкиHTTP/SSE/parser тоже учитываются, если журнал consumption/type2подтверждает списание; type2quota0 освобождает резерв. Одна error/type5запись сquota0 не является окончательным подтверждением нулевого списания: резерв остаётся pending до consumptionдоказательства, поскольку A6API может добавить его позднее. Незакрытые резервы переносятся черезUTCполночь и продолжают ограничивать бюджет. Сверка выбирает только записи с наступившим сроком: после неудач1→5→15→60мин, сведения о попытках иlease сохраняются вSQLite. Записи старше1часа читаются один раз и откладываются на1час, старше суток — на6часов, вместо тройного polling каждуюминуту. Первичная сверка только что завершённого запроса сохраняет короткие повторы. Записи безrequest_id не опрашиваются наугад, отображаются отдельно; error-onlyжурналы и следующий сроксверки видны вдиагностике. Старые недоступные журналы не блокируют новые. Пропавший журнал/ID не считается бесплатным — резерв остаётся pending, фоновая сверка повторяет чтение без повторной генерации. Лимит денег считается как фактические списания+ещё неподтверждённые резервы, а не сумма всех прошлых worstcaseоценок. Данные сохраняются в отдельномBillingStore, дедуплицируются поrequest_id, маленькие суммы считаются с точностью до1нанодоллара с округлением вверх. До внедрения журнал запросов сохранялся неполно; прежние расчётные резервы не превращаются в реальные расходы и не называются списаниями. Фактическая история после обновления помечается как неполная относительно старых проверок. Servercaps и малый лимит тестового токена обязательны.
- После проверки/отмены тестовая подписка паркуется: все положительные caps1, без дополнительного cache-фильтра; fallback и auto остаются выключены. Невозможный cache threshold100% не используется, поскольку платформа может отклонить такой маршрут. Не удаляем последний канал, поскольку это может вернуть default routing. Если write завершился ошибкой, совпадающий readback может подтвердить парковку без повторного PUT. Иначе cleanup фиксируется uncertain; повторное использование возможно только после проверки exact owned ID/version и подтверждённой безопасной парковки.
- Частичный сбой исполнителя не отменяет сохранённые хорошие результаты. При наличии хотя бы одного проверенного подходящего продавца batch заканчивается с предупреждениями и сводными числами; без хороших — ошибка. Публикация рабочего маршрута всегда отдельная: включить политику → Предпросмотр → Опубликовать. Статус проверки не равен публикации.

## Публикация

**Отбор** только читает A6API и сохраняет кандидатов. **Проверить** требует явного подтверждения платных запросов. **Предпросмотр** формирует изменения по прошедшим, свежим и подходящим текущим ценам/кешу каналам.

**Опубликовать** требует отдельного подтверждения и120сек preview; повторно проверяются цена/кеш/TTL, пины, наличие remote route, config_version. Full config write + readback подтверждают exact channels/caps/fallback/auto/cache threshold. Автоматическая синхронизация после свежей проверкивладения сравнивает полнуюконфигурацию: если каналы,лимиты,порядок,приоритеты ифлаги не изменились, PUT не отправляется иversion не увеличивается; локально обновляется только доказательство/времяпроверки. Конфликт или неопределённый исход не ретраится вслепую. При существующем пине публикация заблокирована — рабочие пины не снимаются автоматически.

Ручной режим не публикует автоматически. Явно включаемый автоматический режим публикует после успешных проверок в пределах подтверждённых лимитов. Для remote create безусловная атомарная create-only семантика зависит от A6API; перед вызовом дополнительно проверяется отсутствие чужой записи, backend duplicate конфликт трактуется как conflict, не overwrite.

## Обслуживание и ограничения

**Автоматический режим** настраивается при создании/редактировании отдельно от включения политики. При активации/повышении лимитов интерфейс требует подтверждения будущих платных запросов и автоматических изменений рабочего token+model. Существующие пулы автоматически в режим не переводятся.

- Первый отбор после включения запускается сразу, далее каждые6часов: все страницы продавцов, критерии, до4раздельных тестовых ключей, fingerprint+actual_channel_id, безопасная публикация прошедших доmax_members.
- Каждые60мин проверяются опубликованные участники. Подтверждённый suspect после двух полных низких раундов удаляется из рабочего whitelist сразу после результата, без ожидания остальных. Технический сбой опубликованного участника (SSE,finish,HTTP5xx/429,timeout) подтверждается отдельной второй проверкой в том же общем бюджете; при успехе второй сохраняется участник, при двух технических неудачах безопасно исключается. Ошибка чтения нашей консоли,атрибуции,отмена иbudgetне доказывают неисправность продавца. Неподтверждённые участники после цикла не удерживаются как проверенные. Если состав меньшеmax_members, автоматически планируется добор через60сек при наличии допустимых альтернатив, а не только следующий6часовой цикл. Если все альтернативы на паузе, добор назначается не раньше ближайшего разрешённого повторного теста; баны/суточные бюджеты не обходятся. Явный not-before может отложить уже назначенный ранний добор; причина ожидания (суточнаяпауза/бюджет/временнаяошибка) сохраняется отдельно и показана вАвтоматизации. Это не меняет интервал часовых аудитов или30мин обычного мониторинга. История last_check_status/last_check_reason/last_checked_at сохраняется отдельно от текущей валидностиfingerprint: после изменения политики прежние проверки не выдаются за действующие, но таблица показывает прошлый результат и срок24часовой паузы вместо «никогда не проверялся».
- Четыре подряд завершённых неуспешных seller-check в одном пуле блокируют channel_id. Каждый запуск считается максимум один раз даже при внутренних повторах. verified сбрасывает последовательность; бан сохраняется до явного «Разблокировать». Отмена, budget, attribution/log/admin/cleanup ошибки последовательность не увеличивают.
- Отдельные потолки на запуск и наUTCсутки:USD+число запросов. Резервация денег атомарна, после подтверждения журнала освобождается и заменяется фактическим списанием, в том числе нулевым. Неподтверждённые суммы остаются резервом; счётчик запросов не возвращается при ошибке. Отсутствие бюджета закрывает дальнейшие платные запросы, не банит продавца.
- Расписание, lease, budgets, blacklist и exactremoteownership/version хранятся вSQLite. После рестарта нет догоняющего шквала запросов; один autojob на пул, без перекрытия houraudit/6hrefresh. Ручной запуск автоматического цикла тоже занимает durablelease и сдвигает следующее расписание, поэтому не вызывает немедленный повторный платный запуск. Добор назначается и для пустых пулов/неполногоrefresh, а не только послеаудита. Операционные правки сохраняют все актуальные результаты изБД, включая скрытые лимитомтаблицы.
- Рабочие pins не удаляются. Автоизменения только exactподтверждённой подписки: при optin фиксируется ID/version существующего маршрута, изменение толькоconfig_version при точном совпаденииID,token/model,каналов,caps,сортировки,приоритетов,ratio,cachethreshold иfallback/auto безопасно сверяется безremoteзаписи. Реальное внешнее изменение этих полей останавливает auto до ручного review. Изменение числа участников/кандидатов или бюджета не стирает действующие fingerprintрезультаты; увеличение целевого числа участников планирует добор. Неопределённая запись блокирует localgate, восстанавливается только точным readback.
- Если прошедших нет, локальный gate закрыт. Последнийremoteканал не удаляется: подписка паркуется сcaps1, autofalse/fallbackfalse, чтобы не вернуть A6defaultмаршрутизацию.

Ручные включённые политики по-прежнему обновляют отбор чтением, платные проверки и публикация требуют отдельных действий.

**Прямые запросы в A6API мимо8843 не контролируются локальным gate.** Server caps/cache thresholds продолжают действовать. При проблеме сA6API remoteисключение может не подтвердиться; локальный gate закрывается, но прямые клиенты за его пределами не защищены от такой неопределённости. В ручном режиме whitelist остаётся до подтверждённой публикации обновления. Удалить опубликованную локальную политику нельзя, чтобы не оставить remote route бесхозным.

Цена неизвестна/не USD/per1M/не per-token — автоматический допуск запрещён. Пустая цена/None означает отсутствие пользовательского ограничения для этой категории и сериализуется вA6caps0. Явно введённый0отклоняется: A6API трактует0как отсутствие лимита, а не бесплатный тариф. Для платных тестов незаданные caps замораживаются по известным ценам выбранного листинга на тестовом токене (не0; для бесплатной цены1микро), чтобы бюджет оставался защищён. В опубликованном рабочем маршруте пустые caps остаются без ограничения.

В таблице «Похож на модель» показан наиболее вероятный эталон детектора и его собственная вероятность; соседняя вероятность ожидаемой модели остаётся отдельной. Для ниже-порога это возможное несоответствие эталону, не доказанная идентификация подмены. Неопределённые проверки не получают выдуманную модель. У старых проверок поле может отсутствовать — «Нет данных» до следующей штатной проверки. actual_channel_id сохраняется для проверки атрибуции, но не выдаётся за модель.

В одном пуле до4продавцов проверяются параллельно: по одному worker на выбранный тестовый токен. Один токен одновременно обслуживает только один канал; набор тестовых токенов не пересекается с рабочими или тестовыми токенами других пулов. Бюджет запросов/USD общий на запуск, резервируется атомарно и не умножается на число workers. До4модельных проверок активны глобально, account операций не более2; публикация/редактирование пула не выполняются параллельно с его проверкой. При отмене ожидается cleanup всех workers; старый пул с одним ключом остаётся последовательным. Мониторинг обычных поставщиков остаётся отдельно. На HTTP8843 используйте доверенный туннель/сеть, PAT не защищён транспортом при доступе через Интернет.

## Понятное управление и диагностика

A6API сразу открывает пулы; отдельной вкладки «Продавцы» нет. Внутри выбранного пула отдельные подразделы: «Обзор», «Состав», «Проверки», «Автоматизация», «Настройки». На обзоре видны состояние и основные действия, таблицы продавцов находятся вСоставе, задания — вПроверках, расходы/расписание/баны — вАвтоматизации. Новая политика сразу открываетНастройки; переключение подразделов не сбрасывает несохранённую форму. «Обновить список продавцов» делает только read-onlydiscovery без генерации. «Перезапустить проверку» с подтверждением расходов сначала отменяет текущийjob и дожидаетсяcleanup, потом запускает проверку в прежнем manual/autoрежиме. Успешные свежие проверки, суткиcooldown, баны и бюджеты сохраняются; перезапуск не означает принудительное повторное списание за всех прежних продавцов. «Запустить/Продолжить» явно запускает paidverify; в авторежиме это auto_refresh с обычными дневными бюджетами и автопубликацией, а не обход расписания/лимитов. Ожидание следующего6часового запуска не называется выполняющейся проверкой. Настроено4ключа не означает4активных запроса: фактическое число определяется доступными кандидатами и глобальным gate.

У исполнителей видны время последней активности и этап connecting/streaming/billing/attribution/scoring. Итоги заданий сохраняются вSQLite30дней; воперативнуюпанельзагружаютсяпоследние200. Отдельныйжурналсоставатожехранится30дней:время,добавленные/исключённыеканалы,причина,источникmanual/auto_audit/auto_refresh,job иверсияremote. Онзагружаетсялениво вподразделеПроверки, неувеличиваетвнешниеобращения. Счётчики checked_this_run/passed_this_run/cached_verified/published_members/removed_members отличаютновыепроверкиотстарогоуспешногокеша. После рестарта незавершённые отражаются как interrupted_by_restart, не выглядят бесконечно работающими.

Консоль A6API имеет общий лимит2одновременных HTTP-запросов на аккаунт, старты не чаще150мс. Ответы429/503 запускают общий cooldown поRetry-After до30сек. Повторы не более2 и только GET в пределах общего30секdeadline; POST/PUT не повторяются вслепую. Список токенов кешируется30сек, чтобы polling панели не обращался кconsoleкаждыйраз; pin/subscription/readback не кешируются. Диагностика показывает безопасные счётчики запросов/429/503 и cooldown безPAT, а также фактические попытки и длительности по фиксированным категориям:токены,каталог,маршруты,пины,журналы,параметрыаккаунта,прочее. НикакихURLпараметров,request_idилисекретов втакихметриках нет. Это позволит сравнивать трафик сверки списаний с остальными консольнымиоперациями, не смешивая их с платнымиrelayгенерациями.

### Удаление

Кнопка «Удалить пул» доступна явно. Подтверждение останавливает его исполнителей, дожидается закрытия тестовых маршрутов и отключает расписание. Если есть ранее управляемая подписка рабочего токена, она паркуется сcaps1,fallbackfalse,autofalse с проверкойID/version/readback. Последний канал не удаляется, чтобы A6API не восстановилdefaultrouting. Затем удаляется локальная политика; фактические списания и история сохраняются. Для локального gateway остаётся deny-запись модели+хеша ключа; очистится только после успешной проверенной повторной публикации этого token/model. При конфликте внешнего маршрута/pin удаление останавливается без перезаписи чужой конфигурации. При ошибке parking политика остаётся отключённой, локальный маршрут закрыт; нельзя обещать успешное удаление безreadback.
